# fs-wiki - Design

`fs-wiki` is the wiki program of FreeSynergy and the **owner of the text interface** (ADR 0031, 0050): every text is a wiki
entry, a collection of texts is a wiki. The database is the truth, files are exports (ADR 0042). The contract is `texts.capnp`
in [`fs-interfaces`](https://github.com/FreeSynergy/fs-interfaces) (ADR 0045); this program is its provider. This repo holds
seven crates (one of them only for tests, one the single binary); the GUI lives only in `fs-wiki-app`, on [`fs-components`](https://github.com/FreeSynergy/fs-components) (Blinc):

* `crates/fs-text`: the **library** of text + layers (document, marks, Markdown, outside changes, links, templates, history).
  No storage, no interface. Its own design is in [`crates/fs-text/DESIGN.md`](crates/fs-text/DESIGN.md).
* `crates/fs-wiki-app`: the **first visible part**, a thin shell: imports a folder of Markdown files, maps texts to the neutral
  blocks of `fs-components`, and offers the wiki to the reader workbench as its data source. No Blinc type appears in it. It talks to
  the running `fs-wiki-server` through `fs-wiki-client` (ADR 0021), never to `WikiRepo` or a store.
* `crates/fs-wiki-client`: the **Cap'n Proto client**: `RpcTexts` implements `Texts` + `TextFeed` of the core over a Unix socket.
* `crates/fs-wiki-server`: the **Cap'n Proto server**: the contract `texts.capnp` (fs-interfaces v0.49.1) over a Unix socket, in front of `Texts` + `TextFeed`. It only translates; no text logic.
* `crates/fs-wiki`: the **one binary** (ADR 0063): `fs-wiki` opens the window (and starts the server when none runs, which ends with the last window), `fs-wiki serve` is the server. This is what the release packages.
* `crates/fs-wiki-core`: the **program core**. The trait `Texts` (Rust form of `Texts` in `texts.capnp`) and `WikiRepo`, its
  implementation over `fs-objects`.

## Interface status

**Interface status: draft, consumers: none (0 of 2).** (ADR 0045: the interface is a target; it stays draft until two independent
consumers have tested it, then 1.0, then only version jumps.) Nothing here is declared 1.0.

## texts 0.2 (branch `texts-v2-core`)

The extended contract (`texts.capnp` DRAFT 0.2, methods `@16` to `@35`, fs-interfaces DESIGN.md section "texts 0.2") is implemented in `fs-wiki-core` (trait, then tests, then provider) and `fs-wiki-server`. **fs-interfaces is pinned to `rev = "b83cbb5"` (branch `texts-v2`, version 0.50.0, not tagged) in all four crates that use it; this is temporary and becomes a tag once the contract is tagged.** fs-interfaces 0.50 needs fs-objects v0.5.0, as before. Not touched: `fs-wiki-app`; `fs-wiki-client` only reads the three new fields of `TextEntry` (it does not call the new methods: they stay `Unsupported` there).

### Contract feedback (texts 0.2; what the contract could not support, or leaves open)

1. **History cannot be taken from the activity log.** The log is changed by undo (new `Undo` entries, the undone `Update` stays), compaction and `clear_history` (synced entries go) and purge (all entries of an object go), so neither numbers nor documents are stable there. The contract text ("stored with the text's history, not as a counter inside the text record") is met by separate records; the price is two store writes per text write (three with the first), and the document is also in the log as image of the revision record. Measured on the 1398-page import: see "Import time" below.
2. **`RevisionInfo.number` "1 = the creation"**: for a text written before this version (or whose first record failed) number 1 is the first state this provider knew (summary `state before history began`), not the creation. The contract text could say "the first known state".
3. **`purgeRevision` "removes ONE old revision for good"** cannot be done in the log: `fs-objects` purges per object. The provider purges the log of the whole text (and of the revision record), through the hub way (below). Side effect: the text's own store undo is gone and its later writes are logged without images. `purge_object` rewrites the database file (checkpoint and `VACUUM`) on a disk store at every call and `fs-objects` cannot purge several objects at once, so `purge` of a text with n revisions rewrites the file n + 1 times and syncs with the hub n + 2 times. Wish for fs-objects: purge a list of objects with one clean-up.
4. **`kind`**: the contract says `text` for `not-found` and `conflict`; the 0.1 methods of this server say `page` (DESIGN table below, pinned by `tests/problems.rs`). The 0.2 methods say `text`; `editIf` keeps `page` but now carries `issue`, `revision`, `expected` too. One value should be chosen for both.
5. **`badPathProblemType`: "ext `issue` = "bad-path" plus the reason"** is ambiguous. Implemented: the problem type says bad-path, `issue` is the reason (`empty-slug`, `outside-parent`, `external-target`, `empty-segment`, `dot-segment`, ...), `path` the path. The 0.1 methods still answer `invalid` for the same path errors.
6. **Writes that add a revision**: the contract lists create, edit*, move, import, restoreRevision, setTemplate, setRedirect. This provider also writes a revision for `restoreFromTrash` (it rewrites the text, new `revision`, new `updatedBy`), for links rewritten by a move (`links updated`, as the contract's trash edge cases say), and `setTemplate` / `setRedirect` that change nothing write nothing (the current text is answered). `createFromTemplate` starts a history with `from template <path>`.
7. **Search words** are not defined: here a word is a run of letters and digits (`co-op` is two words, `ä` counts as a letter), the limits of 8 words and 256 bytes are applied to that; relevance is provider-specific and not on the wire. `Snippet.field` `body` is the single block with the most matches (not several blocks).
8. **Space and parent.** "Zero parent = a new space" together with "a page's parent is the folder with the longest prefix" leaves open a space created at a path below an existing folder: here it is a space (parent none), not listed under that folder.
9. **`children` cursor** is an offset of the ordered list; a change between two pages can skip or repeat (the contract allows it). `resolve` does not validate its path (an invalid path is `notFound`). A loop closed after the ninth redirect lists 10 hops, one more than `hops` says for the other outcomes ("at most maxRedirectHops + 1"), because the repeated path is appended. The comment of `Resolution.hops` in `texts.capnp` should read "at most maxRedirectHops + 1, and + 2 for a loop"; this repo does not change the contract.
10. **`delete` leaves revisions behind (privacy).** `delete` (0.1) keeps its meaning, so the revision records of a text removed that way stay in the store, with their documents (an undo of the delete brings the text back with its history). No method purges them: `purge` needs the text in the trash. Whoever must remove such a text for good has to `trash` and `purge` it instead. Open point for the owner.
11. **Trash listing** has no filter and reads the whole trash; there is no retention or expiry of the trash and no feed event for structure changes (folders, order, flags): as the contract's open points say.

### Purge through the hub (Strategy decision, 2026-11-08)

The wiki **never calls `purge_object`**. `fs-objects` says a purge before the sync loses the hub's mark (ADR 0029), so a purge goes the way `fs-hub` allows: `HubSession::sync_then_purge(store, object)` of `fs-hub-client` (v0.4.0), which syncs, checks that no log entry of the object is left unsynced and only then purges. No hub, a failed sync or entries the hub holds back (`Error::NoHub`, `Stopped`, `NotSynced`) mean nothing is purged.

* **Core** (no hub dependency): the port `LogPurge` (`purge.rs`; `purge(id) -> PurgeOutcome | Refusal`, `clean_files`), injected with `WikiRepo::with_log_purge(port)`. `Refusal` is `NoHub`, `NotSynced(id)` or `Failed(reason)`; the core error is `PurgeRefused`. `WikiRepo::new` has no port, so a wiki without one cannot purge. Tested with a fake port that purges in the store (all earlier purge tests), and with one that refuses: `purgeRevision` and `purge` change nothing (the record still reads, the text is still in the trash with its history), a retry completes.
* **Server**: `HubPurge` (`hub_purge.rs`) is the port over `fs-hub-client`; `fs-wiki-server` takes `--hub-socket PATH` (default: the hub's default socket) and looks for the hub at every purge, so one started later is found. **The wiki registers as program `wiki` with `writes(&[])`**: the hub acknowledges what the wiki has and keeps none of it. Measured against the real daemon (`tests/v2_hub_purge.rs`): after `purgeRevision` and `purge` the hub's data folder holds no secret, no `Article` copy and no revision record; with `writes(&["Article"])` the same test fails (the push before the purge copies every unsynced image, old documents included, to the hub, and the hub then holds the purged text as a live copy). `sync_then_purge` still passes its check with an empty list (everything is withheld and acknowledged). Time limits, because the purge holds the write lock: `CONNECT_TIMEOUT` 30 s for finding the hub and registering, `PURGE_TIMEOUT` 120 s per object; on a timeout the wiki stops waiting, releases its lock and answers `no-hub`; the spawned task may still sync and purge the log of the object that was being purged (see "Cancelling", not harmless in every case) (tested with a hub that accepts and says nothing). A dead cached session is dropped and tried once anew; if the hub stays away the answer is `no-hub` 503, not 500 (tested: hub stopped, then restarted).
* **Problems** (outside `texts.capnp`, wiki-local types): `texts/no-hub` (503; also for a hub that does not answer in time) and `texts/not-synced` (409, `id`); a failed sync is a plain failure (500). **Contract feedback:** the contract has no problem type for "the provider could not purge because it is not (yet) safe to"; `texts/invalid` and `texts/conflict` are the nearest and fit badly. Also the capability ids: `text.trash` covers trash, restore, list **and** purge, and `text.history` covers history **and** `purgeRevision`; whether purge is possible depends on a hub being reachable at the time of the call, which a static report cannot say. The report therefore offers them and the two purge methods may answer `no-hub`. A separate id (for example `text.purge`) would be cleaner; not invented here.
* **Limits, plainly.** Because the wiki writes nothing to the hub, a purge does not have to chase copies there: the hub holds none from the wiki (this also means the hub does not collect the wiki's texts at all today; if the wiki ever registers `writes`, the purge copies the secret first, see above). A write between the check and the purge is not covered by `sync_then_purge`; the port does not inspect `unsynced_removed`. Copies that left by another way (export to files, a client that read the text, a backup of the store file) are not touched. The purge syncs the wiki's whole store with the hub first, once per object. **File clean-up:** if the file could not be cleaned after a purge (a reader holds it, or the clean-up failed) the purge is still a success (its object is gone; a retry could only say "not found"); the clean-up is remembered in the store (record `CleanPending`) and repeated by the next purge, by `WikiRepo::retry_file_cleanup` and at server start. Tested with a port whose clean-up fails.
* **Cancelling (tested).** A purge call can be dropped (timeout, client disconnect). `HubPurge` runs `sync_then_purge` in a **spawned task** and waits for it with the time limit: a timeout or a dropped caller stops the waiting, never the sync or the purge, so `fs-objects` is not cut in the middle by the wiki (`tests/v2_hub_cancel.rs`: the real daemon behind a proxy that holds every chunk back 150 ms, so a 100 ms limit certainly fires first; the call answers `Timeout`, and without any retry the log of the first revision record is gone shortly after; a caller aborted once its sync is on the wire does the same; a retry by a program with the normal limit then completes, with the secret in neither the wiki's `.db`/`-wal` nor the hub's folder. **Mutation-checked:** with the spawn replaced by `timeout(..., session.sync_then_purge(..))` both tests fail ("the purge did not run on\)). **A call answered `no-hub`/timeout (or dropped) can still purge the log later; that is not harmless.** The task's sync, check and `purge_object` run without the wiki's write lock (the lock lives in `WikiRepo`, the port cannot hold it without surgery in the core), so a wiki write can run next to it. A write between the task's check and its `purge_object` loses its unsynced log entry (the port logs `unsynced_removed > 0` to stderr; it cannot undo it). Today this is narrow because `fs-wiki-server` runs on a current-thread runtime (`run_until_signal`) and the store's calls do not yield, so a write cannot interleave inside the task's check-to-purge span; that is an assumption, not a guarantee, and a multi-thread runtime or a store that yields breaks it. A hub that never answers leaves one idle task per timed-out call. Also: the late task's `clean_files` result is discarded (a `Busy` clean-up with the `CleanPending` reminder cleared meanwhile by another purge can leave bytes in the file without a reminder); a panic in the task is mapped to `Failed` without dropping the cached session. Without the task, in the wiki's own steps: `tests/cancel_purge.rs` drops `purge` and `purgeRevision` after every number of polls (0, 1, 2, ... until done) with a port that yields between the steps, over a store in a file; "every drop point" means every yield point of that port (the sweep without yields covers only k=0 and k=1). At every drop point: a text still in the trash has its history, a text that is gone has none of its records, the `CleanPending` reminder is set whenever the secret is still in the file, writes work, and a retry completes (`purgeRevision` of a finished revision answers `NoSuchRevision`, the tombstone) with the secret gone from `.db` and `-wal`.
  **Finding for the `fs-objects` owner (not patched here).** (1) Measured on an uncontended single handle on a file: `purge_object` (the whole transaction) never returns `Pending` and finishes in the first poll (under contention `inner.lock().await` and the `Busy` sleep in `begin_immediate` can return `Pending`; not tested). So a `tokio::time::timeout` cannot cut it in the middle, **and cannot fire while it runs** (it also blocks the executor thread; a purge of a big store stalls every task of a current-thread runtime). The cancel point inside the transaction is therefore not reachable today. (2) `in_tx` (`turso/tx.rs`) is not cancel safe by construction: it sends `BEGIN IMMEDIATE`, awaits the step, then `COMMIT`/`ROLLBACK`; if the future is dropped at an await between them (as soon as any call inside yields, for example a turso with asynchronous I/O) the connection stays inside the open transaction, with `inner` unlocked, and the next `BEGIN IMMEDIATE` would fail with a nested-transaction error for the life of the store (reasoned from the code, not reproducible today because of (1)). Wish: a guard that marks the connection dirty on drop and rolls back before the next use (or `spawn_blocking`/an owner task for each transaction). (3) `purge_object` is `async` but does blocking work (checkpoint and `VACUUM` of the file) on the caller's thread; an owner task or `spawn_blocking` would fix (1) and (2) together. The wiki is robust against all three because of the spawned task; a canary for (1) is the poll count printed by `cancel_purge` (`purge finishes after 1 polls`). **What the hub sees:** with `writes(&[])` the hub stores nothing from the wiki, but every sync still sends the unsynced entries, images with old documents included, over the socket to the hub process, which then withholds them. That is acceptable only while the hub is trusted not to keep them; the test reads the hub's data folder, not its memory. **File bytes:** every purge ends with a clean-up of the wiki's own file (`clean_files`), always, because the records the wiki deletes or overwrites after the logs are purged stay in free pages and in the write-ahead log until then; the reminder (`CleanPending`) is written before the first log is purged and cleared after the clean-up succeeded. Tested on a store in a file: the secret is not in the `.db` or `-wal` bytes after `purge` and `purgeRevision` (the tests fail without the final clean-up). A connection loss is only a closed, reset, refused or disconnected connection (`is_connection`); other RPC or I/O errors stay plain failures (500).
* **Redact first: spiked, decided against for now (`writes(&[])` stays).** Spike at store level against the real daemon (`tests/v2_hub_redact.rs`, `fs-objects` v0.0.1, `fs-hub-client` v0.0.1). Works: an object whose content was never synced, marked sensitive (a write), then `sync_then_purge`, leaves the hub with no secret in its folder (the hub gets stubs); the mark can be lifted after the purge by a plain write and the next sync publishes the current copy only, not the purged past (tested). Why it is not clean, in order of weight: (1) **Anything the hub already got in plain stays in its log** (before images of later edits; a mark takes the object off delivery, it does not erase the hub's disk, hub DESIGN "Limit, plainly"; the hub has no purge). Once the wiki registers `writes` and syncs for its live texts, every old version that was ever current at a sync is at the hub for good, so `purgeRevision` of it cannot be honoured; marking first only protects what was never synced. Kept as `content_synced_before_the_mark_stays_at_the_hub`, `#[ignore]`d with that reason (it fails). The only clean policy would be "the wiki syncs only inside a purge, with the object marked first", but then that sync pushes every other unmarked text in plain, and the same problem is there for their later purges. Needs a hub-side forget of an object's log (fs-hub), or an `fs-objects` that does not keep before images for a type. (2) A disk store refuses a mark (`EncryptionRequired`) unless opened with `allow_sensitive_unencrypted` or a key (tested); `fs-wiki-server` opens with `TursoStore::open`. (3) The mark is meant for personal data (ADR 0029): `DpvCategory` is a free string, so any value works, but none says "wiki text"; whoever owns the vocabulary must name one. (4) Cost: a mark write per revision record and per text before each purge, another to lift it on restore from trash (and on a `purgeRevision` of a live text, which must mark and lift the text itself), each an extra log entry and revision of the store; after a purge the object logs without images, so the lift reaches the hub without a `before` image and the hub's rule is that only the marking program (the wiki) may lift it; tested with the wiki itself as the lifter, not with a different program. (5) The hub process still sees the stubs only, which is better than today's withheld plain images. Revisit when (1) has an answer.

### Import time (measured 2026-11-08)

`cargo run -p fs-wiki-app --example timing` against a server on an empty data folder, on a copy of `fs-documentation/docs/en` (1398 pages), **debug build**, one run each, machine load not controlled: import of all pages **64.8 s on main (5b4f2fb), 75.7 s on this branch (+17 %)**; reading a page, `find`, listing: the same within noise (entries 45.0 s / 47.3 s, `find "kanban"` 6.3 s / 6.4 s). The cost is the second store write (the revision record) per text write. No release-build numbers.

### Limits and open points of this step

* **Cost.** `children` / `getFolder` read every record below the parent (the store hands back whole records, so a document is read but not parsed; the top level reads all texts); `search` reads every candidate the store cannot exclude with the longest ASCII word (a term with only non-ASCII words reads all texts); `listTrash` reads the whole trash; `purge` rewrites the database file once per revision record on a disk store. Only `history` / `getRevision` are tested to cost the same in a wiki twice as big (rows read for n and 2n). An index field "folder" on every text would make `children` cheap (not done).
* If the store fails between the write of a text and the write of its revision record, the text is one revision ahead of its history. The next write of that text (or `history`, `purgeRevision`) records the missing state first (summary `state recorded late ...`), under the write lock and after reading the text again. Tested with a failure injected into the revision record (`tests/review_fixes.rs`).
* Order slots are kept by id: a page that is trashed and restored finds its slot again; a deleted folder's order list is deleted with it.

## Types, Admin window, Unsupported (round 3, ADR 0065, 0066, thread R2)

**Descriptions (`fs-wiki-core/src/describe/`, `Texts.types @36` in `texts.capnp`, fs-interfaces v0.0.7).** Each data type of the program implements `DescribesType` (fs-types) and enters the `TypeRegistry`; the server answers `Texts.types` from it (`fs-wiki-server/tests/types.rs`), the client reads it (`RpcTexts::types`). The standard of each type, and why:

| Type | Core value | Standard | Why |
|---|---|---|---|
| `Page` | `TextEntry` | W3C ActivityStreams 2.0 `Article` | the core stores every text in an AS2 `Article` envelope (ADR 0031); the content travels as Markdown. A template and a redirect are states of a page (`kind`, `redirectTo`), as in the contract |
| `Folder` | `Node` (space, folder) | AS2 `OrderedCollection` | a folder holds pages in an order the person sets (`reorder`) |
| `Revision` | `RevisionInfo` | RFC 7089 Memento | a revision is the state of a page at a time; id `<page id>#<number>` |
| `TrashEntry` | `TrashItem` | AS2 `Tombstone` | a deleted object with when and who; id = the page's id |
| `Link` | `LinkEntry` | AS2 `Link` | target and link text; read-only; id `<source>\|<target>\|<place>` (derived) |

`Draft` (the unsaved copy of the reader) is **not** a described type: it is a file of the reader mode, not part of the contract. Listed as `Unsupported`.

**Commands.** Every command of the core is described (Page: create, import, createFromTemplate, change, move, reorder, setTemplate, setRedirect, trash, delete, find, search, resolve, export; the test `describe.rs` compares the list with the methods of `Texts`; Folder: find, create, rename, move, reorder, delete; Revision: find, get, restore, purge; TrashEntry: find, restore, purge; Link: find), and every row of `requirements.md` that the core does not have (below). The list is `find` (an empty term lists, `Backend::list`); `change` is a typed `Edit` (`Backend::change(record, edit)`, kind `Change`, no input; the form is made of the fields of the type that are not read-only, so `id`, `name`, `updatedBy` and `revision` are shown only): a field not in the edit stays, one with no value is cleared, the Markdown is read as an outside change so layers stay. The edit carries no revision: `PageBackend` remembers the revision of every page it listed and writes the content against it, so a write in between is a conflict and never lost (shown as `unavailable`, the frontend has no word for it); a page that was never listed is written against the revision just read. The steps run one after the other (content, kind, redirect, path/move); a refusal stops there and the earlier ones stay. The old `summary` input is gone (an `Edit` has no field for it; the revision note is empty). `setRedirect` not sent leaves the redirect; an empty value clears it. `parent` and `anchor` of a folder name no type (a space has no parent; a reference to the own type would bind the command to a record in the frontend).

## Try it by hand (start instructions)

Start (needs a graphical session). The wiki lives in the server, so **start the server first**, in one terminal; it keeps its data in its own folder (`--data DIR`, default below `$XDG_DATA_HOME`) and listens on `--socket PATH` (default `$XDG_RUNTIME_DIR/freesynergy/wiki.sock`). Then start the app in a second terminal; the first start imports the documentation, about 30 s for 1400 pages (later starts only look at what changed), with a summary line on the terminal before the window opens:

```
cp -r /srv/FreeSynergy/fs-documentation/docs/en /tmp/fs-docs-copy
cd /srv/FreeSynergy/fs-wiki
cargo run --release -p fs-wiki-server -- --socket /tmp/fs-wiki.sock --data /tmp/fs-wiki-data      # terminal 1
cargo run --release -p fs-wiki-app -- --socket /tmp/fs-wiki.sock --docs /tmp/fs-docs-copy --export /tmp/fs-docs-copy   # terminal 2
```

Without a server the app stops with that command line in its message; it never starts a store of its own. Stop the server with Ctrl-C when done.

Things to try, in this order (typing and clicking are not verified by tests; this is the check):

1. The window shows the tree of pages left, the start page (`index.md`) right. Open a few folders with the arrow keys and Enter, or by clicking; the page changes.
2. Follow a link in the text (underlined); `Back` (or Alt+Left) returns.
3. Type a word into the search field (for example `kanban`): the sidebar lists hits; click one. Clear the field to get the tree back.
4. Press `Edit`, change a word, press `Save` (or Ctrl+S): the page shows the change. Press `Edit`, type something, then `Cancel`: it asks once (press again to discard).
5. `Edit`, type something, **close the window without saving**, start the app again, open the same page, press `Edit`: a notice offers `Restore` or `Discard` for the draft. Restore brings your text back; nothing is written until you Save.
6. `Export` writes the page as Markdown to `/tmp/fs-wiki-export/<path>`; pressing it again for an existing file asks first. The documentation folder is never written.

What is known to be rough: emoji that Blinc has no glyph for show as boxes; the first start takes about 30 s; a table with many wide columns may reach past the right edge; the editor text area wraps narrower than its box.

## Decisions

* **Links are resolved against their page in the core when a link is judged for a move or indexed** (changed from the first version, which treated every link as a literal path and broke correct relative links): `[[a/b]]` and `![[a/b]]` stay literal; a Markdown link is relative to its page (`/x` from the root). The `link` index holds the paths a link *can* mean, so `backlinks` finds relative links. The core knows the reader's fallbacks as candidates (`x`, `x.md`, `x/index.md`, `x/README.md`): a page move rewrites a link written without `.md` or to the folder of an `index.md` (`repo/target.rs`, `relink.rs`); link reference definitions (stored as plain blocks) are rewritten with them. The app hands `[[a/b]]` to the reader as `/a/b` (`map/inline.rs`), so one rule holds: wiki links from the root, Markdown links from their page. **Stored form:** `Callout::title` is Markdown as written (changed by fs-text; no real data existed in the old plain form, so there is no migration; an old title like `*a*` would now be read as emphasis). Links in callout titles are found by `repo/titles.rs`, which reads the title with the Markdown parser of fs-text, so only real links count (not code spans, escaped brackets or loose text) and anything else stays byte for byte: in the link index, in `backlinks`, and rewritten with moves (also when their page moves); `links(id)` lists them with `at` = `<block>:title`. The reader shows a title that reads as one paragraph as inline Markdown (formatting, no markup), the whole title strong; a title that begins like a list, heading or quote is shown exactly as stored (`map/title.rs`). A move that makes a text the first candidate of a link that meant another (`z.md` in front of `z/index.md`) writes that link in full, so a correct link is never redirected; for this the sources are also looked up by the new path. Interrupted moves with such links end like the undisturbed one (tested at every write). A real link definition such as `[r]: /private-a` is content: the reader shows it (only comment forms are not displayed). A second definition with the same label is a block of its own (fs-text); `definitions.rs` handles it like any other. A link means the first existing candidate (`repo/shift.rs`): only if that text moves does the link change, and a new form that would lead to another existing page is written in full (`b.md`). For this a move reads the paths of all texts once (memory: the paths only). A dangling link into a moved folder still follows it. Limits: percent-encoding is not decoded when matching a moved path. Link reference definitions are found only in blocks fs-text marks `unparsed` (`definitions.rs`; text in `<pre>` or a comment is never rewritten), also with the destination on the next line; a new destination with a space is wrapped in `<...>`; definitions count in the link index. **Not displayed**: link-definition comments (`[//]: # (note)`, `[note]: # (text)`, `[x]: <> (text)`) and HTML comments (`<!-- note -->`) are not shown by the reader and not found by search (`is_hidden_block`); this is no secret: the editor shows them and every export contains them.
* **The app is read, edit, export:** save goes to the database (`Texts::edit`); a file is only written by the explicit Export action (ADR 0042, 0046). A session that only reads and edits leaves the docs folder unchanged (tests `import`, `source`).
* **The database is the truth** (ADR 0042): `WikiRepo` never writes a file. `export_text` returns the text; the caller writes it.
  A file that comes back is an `import_text`, which is a diff, not a replacement.
* **A text's path is part of the record**, and indexed. A move changes the path of one text and the *links* in others, nothing else.
  A path never contains U+10FFFF (it ends the order range that lists a folder, so such a text could not be listed or moved).
* **Derived data is only in the index** (`path`, `link`, `block`): the record can always rebuild it.
* `fs-text` stays free of storage; the core uses its public API only (`Document`, marks, `Op`); other changes there are in its own DESIGN.md.

## Open points

Open points of 0.3.0 (honest list):

* `moveFolder` still answers `too-large` after the move was done when the moved texts together exceed one message (the text says how to read them). The cursor-less answer is the contract's.
* `fits` no longer builds the JSON string, but Markdown is still parsed twice per import (once to measure, once in the core): about 0.4 ms per page, small against the store.
* `fs-objects`: an exact index lookup is O(n), and `order_by_index` sorts every candidate before it cuts. Pages stay linear in rows read, but each page query costs the store O(texts left). Reported, not changed.
* `upgrade_index` moves `updated` of a repaired text (it is a write); `revision` and the document stay.
* The cursor module is a copy of the one in `fs-tasks-server`; one shared implementation belongs in `fs-interfaces`.
* `fs-wiki-app` and `fs-text` were not changed. The app is built on `fs-components` v0.2.0 (the tag v0.4.0 that thread 1 may use does not exist on GitHub yet).

First visible part (provisional, for the owner): the name of the reader and of the `fs-components-*` crates; `index.md` as the start page; the sidebar shows page titles, folders their name; import problems as a first tree entry; search results capped at 200; the Export folder is explicit (`--export`), never implied.

Measured on a **copy** of `fs-documentation/docs/en` (1398 pages, 510 folders), release build, 32 cores, **while the machine ran at load 20 to 64, so the numbers mean little** (`cargo run --release -p fs-wiki-app --example real_docs <socket> <copy> <folder> <new path>`, older numbers: they were taken with the core inside the app, before the socket): the first start into an empty store file took 76 s (the same code at load 64: 183 s; the code before this change, load unknown, 44 s in the same kind of run; an unloaded run of the older code gave 27 s in memory). Writing a record per file costs extra on the first start only. **A second start with nothing changed takes 58 ms** (before: 30.4 s, every file was parsed and diffed); a start after a folder move 40 ms and the moved folder does not come back. Moving `interactions/gestures` (76 texts) took 4 to 17 s depending on load. Links leading nowhere (3794 internal links, resolved as the reader does): 104 before a move and 104 after; the code before this change went from 104 to 131 (27 newly broken) and brought the 76 moved texts back at the next start. The store file is 56 MB. **The reader calls the source on the interface thread** (`examples/timing.rs`, older numbers, other machine state): list of all pages 284 ms once at start, `get_by_path` + mapping of a page 20 ms, `find` 34 to 59 ms per search keystroke; not measured again.

Server decisions (provisional, easy to reverse):

* **`links` / `backlinks` answer every link** (contract 0.39): `LinkRow.title` is the link text as written, `internal` is true for a target that is a text of this wiki (it may not exist yet) and false for an outside address (URL, mail). The target stays as written, with `#fragment`. Before 0.3.0 outside links had no row. The lists have no cursor: an answer above one message is `too-large`. `TextEntry.revision` is only compared for equality (`editIf`); it is no counter and no time.
* **`find` with an empty term is refused** (422), not "everything".
* **`list` / `find` pages are cut in the store** (0.3.0). The cursor is a place (form byte 2 + sort key, name, id), not a position: a text added or removed elsewhere changes neither what was read nor what comes next. A cursor of the old form (byte 1) is refused as `invalid-request`. The query is ordered by `path_key`, because the store's conditions compare the raw value and its order uses the folded value; with the folded value stored as the value both agree. Two paths that fold to the same key (`Alpha`, `alpha`) are told apart by name, then id. The page also stops by weight (`fitting`); an item above one message is `too-large` with the cursor past it.
* **Why the import of 1398 files did not finish (found 2026-11-07).** `text_at` (path lookup before every create / import) and `aux_get` (the file record) were queries with `order_by_index`: the store computes the sort key of every text for each lookup, so a lookup costs O(n) and an import O(n^2) (debug build, whole documentation: minutes). A path or a key names one object, so both lookups are now unordered with `limit(1)`. Measured on 50..400 real files of `fs-documentation` (debug, loaded machine): import 50 -> 1.7 s, 100 -> 4.1 s, 200 -> 11.4 s, 400 -> 37.8 s before; 100 -> 2.0 s, 200 -> 3.6 s, 400 -> 8.4 s after (parse alone: 0.18 s for 400). What remains is the store: an exact index lookup is still O(n) there (about 2.6 ms at 100 texts, 5.5 ms at 400), reported for `fs-objects`, not changed here. `moveFolder` and `backlinks` use ordered index queries too (one per move, not per text).
* **The server parses on the thread that serves all connections.** Hence the 4 MiB limit on Markdown. A document is large (one-letter paragraphs: 105 times the Markdown), which `fs-text`'s serde form could shrink (thread 1).
* **`moveFolder` is answered with all moved texts**, as the contract says; above one message it answers `too-large` after the move was done.
* **`media_type`**: only `text/markdown` is known; any other is `Unsupported` of that method, though the report lists the capability as offered.
* **Problem extensions** (keys of `fs-interfaces` `problem_keys`; the detail text is unchanged; `server/facts.rs`):

  | Problem | status | `id` | `kind` | `issue` | `path` | `size` / `limit` |

  | `texts/not-found` | 404 | the text | `page` | | | |
  | `texts/not-found` (no text at or below a folder) | 404 | | `folder` | | the folder | |
  | `texts/conflict` | 409 | the text | `page` | | | |
  | `texts/path-taken` | 409 | | `page` | | the taken path | |
  | `texts/move-refused` | 409 | | `folder` | | the target in the way (unfinished move: the folder) | |
  | `texts/invalid` (path) | 422 | | `page` | token of `Reason` (`empty`, `fragment`, `empty-segment`, ...) | the path | |
  | `texts/invalid` (folder move) | 422 | | `folder` | `inside-itself`, `inside-old-folder` | the folder | |
  | `texts/invalid` (request) | 422 | | | `path-empty`, `term-empty`, `document-unreadable`, `media-type` ... | | |
  | `too-large` (source, document, moved texts) | 413 | | | | | bytes / limit |

* **`CONTRACT_VERSION`** is `texts 0.1 (draft)` (the schema header says DRAFT 0.1).

Questions for the owner (all provisional, easy to reverse):

* **One server is one wiki.** The app has no store of its own any more, so two documentation folders in one server would share one text namespace. Use one server (own `--data` and `--socket`) per documentation source, or tell me if the app should prefix paths per folder.
* **Records and servers (provisional; thread 1 decided).** The records file keeps the records of each store it has seen (`SupportReport.instance` from the store's identity in `fs-objects`, read by `Texts::identity`). That settles "every text of a folder was deleted outside the app", but **not** "a server restored from a backup that has only some of the texts": that has the same id, and stays **open**. What is done now:
  * The check at every start asks the server, once per record, whether the text is there (`get`, 64 at once on the one connection, the whole check bounded by 60 s; a stuck server ends the start with a failure, tested). A listing would be one call, but it carries every document and took 5.5 s for 1398 pages; so the cost is about one second per 3000 records. **Measured** on a copy of the documentation (1398 pages, release build): first start 60.5 s; second start **about 390 ms** (375, 402, 391 ms; 16 ms before the check existed; 542 ms with one `get` after the other). The goal of 100 ms is not reachable with this contract: it needs a call that answers "which of these ids exist" without documents (wished for from the strategy: `exists(ids)` or a list of ids and paths).
  * One `get` that fails does not stop the start: that text is taken to be there (as the records say) and the file is reported as its own entry on the problems page ("not imported" list, with the reason). The check stops with a message only when it runs past the 60 s, or when **every** `get` of at least two records fails (the server is not there; with one record a failed `get` cannot tell, so that file is reported like any other and the import goes on; tested: `the_only_record_whose_read_fails_does_not_stop_the_import_either`). Each answer is reduced to a yes or no at once, so no document is kept in memory (tested: `check_single`).
  * **Whose records they are is the store's identity, not a guess.** The records file keeps the records of each store it has seen, each section after a line `{"store":"<uuid>"}` (`Origins::belong_to` selects the section; `Texts::identity` of the server comes from `SupportReport.instance`, which `RpcTexts` reads at the handshake). Going from server A to B and back to A brings A's records and their `deleted` marks back (tested). A server with no records of its own yet ignores those of the others (`Report::records_ignored`, said on the terminal) and imports every file. The same store whose texts were all deleted **outside** the app is the same wiki: the files are listed as missing and not imported again (tested). **Records from before the store line existed** (header-less, at the start of the file) are taken over only when the server has at least one of their texts (one deleted on purpose does not count; `Origins::adopt_legacy`); otherwise they are another wiki's, the file is not bound to this server by them, and the files are imported again (tested both ways). **A provider that tells no identity** (`identity()` is `None`) cannot show that records made for stores are its own: if the file holds records of stores, they are ignored (tested). With no stores in the file it is trusted; with stores in the file its records get a section of their own (a fixed placeholder id), trusted at the next start (tested: a text deleted in the app stays deleted over two starts). The old rule ("the server holds none of the texts the records name") is gone. A restored copy of a store keeps its id and stays as described below.
  * **The old per-app store file** (`<data>/freesynergy/fs-wiki/<folder>-<hash>.db`, used before the wiki moved into the server) is not read and not migrated; the app names it on the terminal at the start when it exists (`store_path::old_store_file`, `words::OLD_STORE`).
  * A text is missing while others are there: the file is **not** counted as unchanged and **not** imported again; it is listed in `Report::missing` and on the problems page ("Missing on the server"), and the terminal says how many (tested with a restored copy and with a text deleted outside the app). It stays listed at every start, because there is no screen yet where the person can confirm it. A text deleted through `Wiki::delete` marks its record (`FileOrigin::deleted`): that file counts as unchanged and is not listed. **Today this does not apply in the real program:** the app has no way to delete a text (the reader's `DocumentSource` has no delete), so only code that calls `Wiki::delete` (the tests, a later screen) uses it. If the text is deleted and the record cannot be updated, the error says so ("deleted on the server, record not updated"; the text is gone and the file will be listed as missing). For texts deleted outside the app, or lost by a restored copy, the list stays until the file is changed (then it is a conflict, as before) or the record is removed by hand.
* **Dead connection and the feed.** Only a connection that is really gone is dead: the server closed it (`Disconnected`) or the connection thread ended (`Fault::Gone`). Then no feed can be made on it: `subscribe` tells the new listener `ended` (not inside `subscribe`, but from a thread of its own, one listener at a time with 100 ms between) once per listener object, so a listener that subscribes in `ended`, even a fresh object each time, hears it at a bounded pace and never recurses (tested on a thread with a 256 KiB stack; without the fix the loop ran about 550 000 times in 3 s). A dead connection never revives: make a new `RpcTexts`. A subscription that fails otherwise (the deadline runs out, the server refuses) fails that one attempt: the listeners are told `subscription failed: ...`, the connection stays usable and the next `subscribe` tries again (tested with a busy server and a 1 s deadline). Subscribing from inside a listener callback (the connection's own thread) cannot wait there; another thread waits and settles the result.
* **Open pattern questions.** `fs-wiki-client/src/feed_job.rs` is named Observer + Command, but it is free functions with effects (mark dead, end the feed, start a delivery thread); `fs-wiki-app/src/origins_log.rs` is `Pattern: none` and is free functions on a file (parse, atomic rewrite, lock) with effects. If the table of coding.md §2 has a better name for "the storage of a Repository, kept in a file of its own" or for "delivery of a notice from a queue", these are the two to rename.
* **Open: sentences of the app in code (§2a).** The sentences of the server connection, the records and the check are in `words.rs` (`say` fills named places in one pass). Still in the code, to move one by one: those in `source/problems.rs`, `sync.rs`, `import.rs` (the "cannot read the record of earlier imports" and the gone-file reasons), `drafts.rs`, `drafts_orphans.rs`, `source/export*.rs`, `source/wiki.rs`, `source/resolve.rs` and `main.rs` (the conflict reason for orphan drafts, the stats line).
* **Limit: the client reads problems from their text.** `fs-wiki-client/src/problems.rs` tells some variants apart by the text of the problem (`the move of ...`, `invalid path ...`, `unknown media type ...`), because the server sends only a type, a status and a text. Wished for from the strategy: problem types of their own in the server for these cases (`texts/move-unfinished`, `texts/target-not-empty`, `texts/invalid-path`, `texts/media-type`), so that no text is compared.
* **Records lock.** `FileOrigins::open` takes an exclusive lock (`File::try_lock`, the same on every system; the lock file is opened for read and write, which Windows needs) on `<records>.lock`: a second app on the same docs folder is refused at its start (`OriginsError::Busy`, a type of its own; the lock is held until the last write of the file has ended, also after the value was dropped). The helper files (`.tmp`, `.lock`) are named after the whole file name, so `a.origins` and `a.json` do not share them. Two apps on different docs folders use different files, but if they use the same server their texts share one namespace. The write and sync of a record run on a blocking thread (`spawn_blocking`).
* **Folder move answered `too-large`.** The server has done the move when its answer would not fit; the client then reads the state (nothing left at the old place, texts at the new one) and returns the moved texts, as the core does. If the state says the move did not happen, the error stays.
* **Paging under writes.** The cursor is a position in the list at the time of the call, not a snapshot. A text created, deleted or moved between two pages of one `list` / `find` can make an entry appear twice or be missed in that one answer. Read again if it matters.
* **Records file** (`FileOrigins`): JSON lines next to the app's data, one file per docs folder; the simplest thing that survives a restart and writes atomically. A different place (a store object of the server) would need a contract method for it. Two programs on one file: refused (lock, above).
* **A folder link without an index page** opens the first page of the folder (by path); a folder with no page is Missing.
* **A conflict** (file and text both changed) keeps the database text and shows the file's version on the problems page every start until the text equals the file; there is no "take the file" button yet.
* **A file that is gone** keeps its text and is listed; its record stays.
* **Export into the docs folder after a move** leaves the old file and says so.
* **A file emptied outside** (or holding only a byte order mark) while its text has content is a conflict, not an edit.
* **Drafts** of a page that moved or was deleted are listed on the problems page (never lost, not moved automatically); an empty or relative `XDG_DATA_HOME` is treated as unset.
* **Hidden folders** (`.git`) and non-Markdown files are skipped without a note; symbolic links, `.MD` and unreadable entries are listed.

* **Stored media type** `application/vnd.freesynergy.text+json` and the record shape `{ path, document }`: ADR 0034 asks for a
  neutral name for the block specification; this is a placeholder until it exists.
* **`LinkEntry.at`** is `<block id>:<start>-<end>` (char offsets). The schema only says "where in the source".
* **Envelope type:** every text is an `Article`; the schema also names `Note`. When is a text a `Note` (short, no heading)?
* **Original of an imported file** (ADR 0030) is not kept: only its hash and the hash of the text at that time (`FileOrigin`). A conflict shows the file's current version once per start, until a person resolves it (a save that makes the text equal the file clears it).

Not done / limits:

* **Uniqueness of `path`** holds inside one process (write lock). Two programs writing the same store at once can still race; the
  store has no unique index (a wish for fs-objects).
* **A move is several writes** (other texts, then the moved text); `fs-objects` 0.2 has no transaction over several objects. Repeating
  an interrupted move finishes it. Each write is one undo step.
* **A folder move** (`move_folder`) is `n` writes, in this order: (1) every text outside the folder that links into it, found by the
  `link` index (equal to the folder or in the range `folder/`), (2) the texts of the folder, shallow ones first, each once with its
  new path and its links already rewritten. Before the first write the whole plan is checked from reads (a target taken anywhere:
  `PathTaken`; target inside the folder: `InvalidMove`; no text at or below: `NoSuchFolder`; same path: nothing, the texts are returned).
  What a reader sees in between: during (1) other texts already link to the new paths, which do not exist yet (dangling for a
  moment); during (2) some texts are at the new path, the rest still at the old one, and a link between a moved and an unmoved text
  points to the new path, so it is dangling until the end. No text is missing or twice at any time: each write replaces one text
  under the same id. If the call fails in the middle, the state stays like that until the same call is repeated; it plans again from
  the store and does what is left, nothing twice. Tested by failing the store after every number of writes.
  Limits: a target that would put a moved text inside the old folder (moving `a/b` to `a` while `a/b/b/x` exists) is refused, because
  after an interruption a moved text could not be told from an unmoved one. Two programs on one store can interleave (no lock
  across processes). Planning keeps only ids and paths of the folder in memory (read 500 at a time with offset paging, O(offset));
  the outside texts linking in are read in one query each for `folder` and `folder/...`.
* **Undo of a folder move:** the store undoes one write per step (`undo(actor, n)`), not one move. Undoing all `n` writes (the outside
  texts and the moved texts) restores paths and documents; undoing fewer leaves a half moved folder, the same state as an interrupted
  move, and repeating `move_folder` finishes it again. Tested both ways. A single "undo the folder move" needs a group of activities
  in fs-objects (a wish).
* **Deleting a text** leaves links to it in other texts (dangling, like in any wiki); they are shown as links to a path with no text.
* `LinkValue.target` (UUID of the target) is not filled; links resolve by path.
* `find` is substring only (no tokens, no ranking) and also searches code blocks.
* **Client limits.** `RpcTexts::page` (a page after a place) hands the server the cursor of the place (`fs_interfaces::rpc::encode_place`, fs-interfaces v0.49.1), so nothing before the place is read and the cut is the core's (key, name folded, id); paths that differ only in case are all returned (tested against the provider itself, `tests/place.rs`); `list` / `find` cost a full read for each page as before. `LinkRow.title` and `internal` are read as the server sends them (fs-interfaces v0.49.1). `TextFeed::subscribe` answers `Unsupported` when the server's report lacks `text.subscribe`. `InvalidMove` is read from the `issue` extension of the problem (the reason's token), the prose is only a fallback. `too-large` has no variant in `Error` and arrives as `Store(Invalid("too large: ..."))`. A feed cannot be dropped per listener on the server: dropping a `Subscription` removes the listener locally, and the one remote subscription runs until the connection ends. The first `subscribe` blocks for one round trip; from inside a listener callback (the connection's own thread) it only queues the request, so it cannot lock the connection. Each remote subscription has a generation: the late end of an old one does not end a newer one. A `ChangeListener.ended` or a lost connection is told to every listener through the new `TextListener::ended(reason)` (default: nothing; `Registry::end`), after which the next `subscribe` starts a new remote subscription; changes may have been missed, read the state again.
* **Core change for the client:** `TextListener::ended` and `Registry::end` (additive, tested in `fs-wiki-core/tests/feed.rs`). `fs-interfaces` is v0.49.1 in all crates (shared client `Worker`).
* Not verified: a failed append of the records file (no way to make the disk fail in a test); typing in the real window against a server.
* `TextFeed::subscribe` returns `Result<Subscription, Unsupported>`: a provider whose report lacks `text.subscribe` says so (tested with a fake feed).
* Offset paging (`Paging`) costs O(offset) in the store; the wire `Cursor` will wrap the offset.

## Markdown round trip

The property `markdown_model_is_stable` (import, export, import gives the same content) holds for the inputs the test generates (a fixed set of fragments, not all of Markdown); the check on every file of the documentation tree is `tests/real_docs.rs`, which is `--ignored` and was not run for this section. Real text stays clean: `2 * 3`, `snake_case` and `a_b` get no backslashes.

* **Runs of delimiters.** CommonMark pairs `*`/`_` runs by flanking and the rule of three, which no
  local escaping rule predicts. `inline` therefore writes the plain, escaped form first and reads
  it back; only when the text or the emphasis differs, other writing variants are tried (`variant`:
  a literal delimiter char joins the run before an opener or after a closer, an emphasis keeps its
  `*` behind a `*`) and the first one that reads back right wins. Text that already reads back is
  untouched. A `_` span stays `_` when punctuation (a link end, a `*` closer) stands next to it.
* **Empty quote.** `>` is something the person wrote, so it is a block: an empty paragraph inside the
  quote (like an empty list item). It also keeps the lists around it apart.
* **Adjacent lists.** Two lists of one type with no block between them (for example around a link
  definition, which is not a block) would read back as one. The export puts `<!-- -->` between them,
  the usual way to say it in Markdown and invisible in other tools. The importer does not keep this
  comment as a block when it stands between two lists, because the model already says "two lists"
  (a different list marker needs no comment). Every other comment stays an HTML block.
* **Loose lists** are also recognised by a blank line before the next item (`*`, `* #`), not only by
  a paragraph in an item. A nested tight list in a loose item gets its blank line.
* **Thematic break** behind a `-` marker is written `***` (`- ---` is one rule, no item).
* **Wide table rows.** Cells beyond the header width are dropped by the parser; the importer reads them
  from the row's source and widens the table (empty header cells), so no text is lost.

`tests/real_docs.rs` (`--ignored`) imports and exports every file of the documentation tree and
checks that no word is lost and a second round is stable. Link reference definitions
(`[x]: /url`) are not part of the model and are still not written back.

## Language variants and component blocks (2026-11-12)
**Language variants (page level).** DE and EN are ONE page with variants (`variants.rs`, `source/pages.rs`). A page has an id (UUIDv7, made once and kept in `<records>.pages`) and per language a variant `{text, path, rev, source_rev}`; `source_rev` is the revision of the ORIGIN variant a translation was made from; if the origin has another revision now, the translation is outdated (`PageIndex::outdated`; equality, not order, because a revision is "never used twice", not promised to count up). A translation seen for the first time, or one whose text changed since the last linking, is "in step" with the origin as it is then; one that did not change keeps its `source_rev`, so a changed origin makes it outdated. The origin language is set per family (`--origin-language`, default `en`; `adr` is `de`). The texts stay one per variant and file (`en/<path>`, `de/<path>`), so the round trip is byte for byte and an export writes the two files again. **This is the page level of ADR 0072**: the block level adds a block id per language with `translationOf` and the same `sourceRev` in the same words, later, without changing these names. **Need reported (no change made):** `texts.capnp` has no field for the grouping, so other frontends of the same server do not see variants; a later `variants` (page id, language, `sourceRev`) in the contract would move `PageRecord` into the server (additive). fs-interfaces v0.0.19 stays as it is.
* **Reader.** One sidebar entry per page (`docs/x.md`, `adr/…`, `research/…`), titled in the language read in. A language bar at the top of a page with several variants (`Language: **Deutsch** | English`; the others are links `?lang=xx`, resolved by `WikiSource::resolve` to `docs/x.md@xx`, which also makes that language the one for the next pages). A page without the chosen language is shown in the origin (else the first there is) with a notice ("Diese Seite gibt es nur auf Englisch." / "This page is only available in German."); an outdated translation says so. The sentences are in `lang_words.rs` (DE and EN). Links between pages are resolved between the texts and lead to the page. A search hit found in both languages is one hit.
* **Measured on the real documentation** (`variants_real.rs`, `FS_DOCS_ROOT=<checkout> cargo test --release -p fs-wiki-app --test variants_real -- --ignored --nocapture`): **2378 pages, 1821 in two languages, only en 440 (docs) + 45 (research), only de 0 (docs) + 72 (adr), 4199 variants; outdated at first sight 0; 4199 of 4199 variant files byte-identical, 0 different, 0 failures.** (So `docs/en` has 440 pages `docs/de` does not have.)

**Component blocks (model only).** A page may hold living components (task board, map, calendar, form, people, files ...) that work as in the program (ADR 0066: everything that shows is a component, the settings decide the data source; ADR 0072 blocks). `fs-text/src/component.rs`: a block kind next to text: `ComponentSpec { component (typed id), version, config (JSON), source: { setting, params } }` plus the static fallback, which is the ordinary Markdown between the markers. In Markdown: `<!-- fs-component {json} -->` … fallback … `<!-- /fs-component -->`.
* **Why HTML comments (and not a fenced block with an info string).** A comment is invisible in GitHub, mkdocs and any viewer, and the fallback between the markers is plain Markdown that those render as it is, so the page reads complete everywhere; a fence would show the configuration as code to every reader that does not know it. A comment is an `Html` block the importer already keeps verbatim, so the round trip needs no new rule: untouched blocks come back from their kept source, changed ones from the canonical writer (it puts blank lines around the markers, which read back the same). A `--` in the JSON is written `--`. A marker that does not read, or is not closed, stays a comment and is named (`find_components`).
* **Nothing changed for existing pages:** no page of the documentation contains the marker; the 4199 files are byte-identical as before (re-measured). Tests: `fs-text/tests/component.rs` (round trip, canonical writer, edits around it, bad markers) and `fs-wiki-app/tests/variants.rs` (a page with a component block in both languages, through the real server, byte for byte).
* **Rules for the program that draws it (not built).** A component block shows only what the viewer may see (the viewer's rights, not the author's); on the public website only data that is released publicly (no source reference is followed there without the release); on the web it lives through Blinc-Web (Wasm), otherwise the static fallback is shown (export, no JS, search engines); the configuration is data, never code; an unknown component type or a higher version shows the fallback and says so.

**Noted for later (not built): the wiki IS the website.** HTML export plus Zentinel: page templates and layouts, navigation and menu, pretty URLs, SEO basics (title, description, sitemap), theme (`docs/assets` belongs to the theme import, not to a page as an attachment). Every program has at least two frontends; for the wiki: C reading mode (today), A Wikipedia-like, B Obsidian-like, with pictures next to the model, after the milestone. Attachments: after the milestone the wiki stores them itself, content-addressed (BLAKE3) in its own store, the owner after ADR 0050, later offered through `storage`.

The server also closes every descriptor above stderr that it inherited (`detach.rs`, Linux, first thing when `--lease` is given): `Command` closes only close-on-exec descriptors, and a lock a build tool passed on by hand was kept open by the detached server for as long as it lived. `crates/fs-wiki-server/tests/detached.rs` proves both with the real binary (a descriptor 9 opened by a shell before the exec is gone; the server ends when the lease folder is removed); `crates/fs-wiki/tests/start.rs` has the guard `Home` that ends every server of its test on drop (also after a failed assertion) and a test that no `fs-wiki serve` of its socket folder is left.

## Frontends (2026-11-13, version 0.0.8; called "faces" until 0.0.9)
The reading wiki (`--read`) opens a window of `fs-components-app` (`frontend_window.rs`): one screen with the reader widget of `fs-components-workbenches` v0.0.13 as its surface and the menus Program (Quit) and View, whose lines are `Frontend: Classic | Confluence | Notion` (German `Ansicht`, the lines the same), the shown one marked with a check. Choosing a line puts a clone of the same `ReaderWidget` (the state is shared: page, search, history, an edit in progress) into another `Layout`, switches the `bare` flag of the source (a frontend with its own head draws the language bar and the notices itself; Classic needs them in the page text, so the shown page is read again unless it is being edited), saves the choice and sets the menus again, which draws the window anew with the mark on the new frontend. There are no sub-menus in the shell, so the "Frontend" of the menu is part of each line.
* **Remembered:** one word (`classic`, `a`, `b`) in `<data>/freesynergy/fs-wiki/frontend`, written under a temporary name and renamed over (`frontend.rs`, the pattern of `heads.rs` and `variants.rs`). A missing, empty, non-UTF-8 or unknown content is read as nothing: the default. A failed save is said in the status line and on stderr; the window goes on with the frontend it has. **Migration (0.0.9, the old name was `face`):** `frontend` is read first; only when it does not exist is the old `face` read, and a valid word is written as `frontend` (atomically) and returned; the old file is never deleted. A broken `frontend` is the default, the old file is not asked then.
* **Default of a new installation: Confluence (A)**, because the page tree and the outline help most in a documentation of 2400 pages. `--frontend a|b|classic` beats the file for one run and never writes it. A snapshot (`--snapshot`) reads no setting: only the override, else Classic, so pictures repeat.
* **Tests:** `tests/frontend.rs` (save, load, broken file, migration from `face`, menu lines in both languages without "Face"/"Gesicht", `AppWidget::choose` of each line: file, mark and `bare` switch), `src/frontend.rs` (override beats file beats default). Not tested: the pixels of a switch in a real window (no desktop session in the build slot).
* **Limits (from the second wiki round, unchanged):** the history shows only the current version; the UUIDv7 of a page is not shown; component blocks are not drawn as cards (their Markdown fallback is the text); the block editor has no `/` menu (the hint mentions it, the key does nothing yet); `Texts::list` over RPC is slow on the whole documentation (about 100 s), so use `--index FILE` or `FS_WIKI_CALL_TIMEOUT`; `Texts.listHeads` (heads only) comes with fs-interfaces v0.0.20 and replaces the index file.
* **Not done, needs fs-components:** the page icon above the title in Notion is a grey page symbol when `PageInfo.emoji` is empty (it should be larger and, without an emoji, empty space; `view/wiki/notion.rs::page_icon`). The icon is drawn in the library; this repository cannot change it without a new tag of fs-components, and `PageInfo.emoji` has no source in the wiki yet.
